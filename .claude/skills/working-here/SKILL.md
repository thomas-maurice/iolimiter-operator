# Working in k8s-blkio-limiter

## Layout

| Path | Content |
|---|---|
| `api/v1alpha1` | `IOLimiter` (user-facing) and `PodIOLimit` (internal, controller-written spec / agent-written status) CRD types. |
| `internal/controller` | Manager-side reconcilers: `IOLimiterReconciler`, `PodReconciler` (stubs until C4), plus the envtest CEL suite. |
| `internal/agent` | Node agent: `Main(ctx, args) int` (the `agent` subcommand), `PodIOLimitReconciler` (SPEC.md §6.1), volume resolution, D24 health checks, metrics. From C2. |
| `config/` | kustomize: scaffold `default`/`crd`/`rbac`/`manager`/`prometheus`/`network-policy`, plus `config/agent/` (DaemonSet, SA, `agent-role` RBAC), from C2. |
| `test/e2e/harness` | Shared e2e helpers (build tag `e2e`, plain package): pinned-context clients, kind/DaemonSet/Deployment plumbing, PV/PVC/Pod/StatefulSet/IOLimiter/PodIOLimit builders. Imported by both suites below, never duplicated. |
| `test/e2e/agent` | kind e2e, agent-only: hand-crafted `PodIOLimit`s (C3), controller-manager scaled to 0 for the package. Writes to the main resource go through `harness.ControllerClient` (C7/D27: the VAP only allows the controller SA to write it). |
| `test/e2e/operator` | kind e2e, controller-driven: every test goes through a real `IOLimiter` (C5), controller-manager running. |
| `test/e2e/hardening` | kind e2e, C7: the `ValidatingAdmissionPolicy`s (D27) and the narrowed agent cgroup mount (D28), against the real, unmodified deployment (neither the controller nor the agent DaemonSet is scaled/patched). |
| `dist/chart` | Helm chart (checked in), regenerated by `make helm-chart` from kustomize output (kubebuilder `helm/v2-alpha` + `hack/helm-postprocess.sh`, C6). |
| `.claude/skills/working-here` | This file. |

## Kind cluster

Every kubectl/helm invocation in the Makefile goes through a **pinned**
context, `kind-$(KIND_CLUSTER)` (`KIND_CLUSTER` defaults to `blkio-limiter`).
Never call `kubectl`/`helm` against your ambient context when working on
this repo — a wrong-context apply is exactly the failure mode the pinning
exists to prevent.

Tool versions are pinned in `.tool-versions` (asdf): kind 0.32.0, helm
3.21.3. If `kind` says "No version is set", run `asdf install kind 0.32.0`.

```sh
make kind-create        # create the pinned cluster (idempotent), hack/kind-config.yaml
make kind-loopdev       # idempotent: two 512Mi loop devices on the worker (disk0/disk1, hack/setup-loopdev.sh)
make kind-storage       # apply the blkio-local StorageClass (hack/e2e-storage.yaml)
make kind-load-busybox  # pre-pull busybox:1.37 into every node's containerd (ctr images pull, not `kind load`: see below)
make kind-setup         # kind-create + kind-loopdev + kind-storage + kind-load-busybox
make kind-delete        # tear it down
make kind-reset         # delete + kind-setup, from scratch
make kind-load          # kind load docker-image $(IMG)
make deploy-kind        # docker-build + kind-load + deploy + rollout restart, waits for rollout
```

`hack/kind-config.yaml`: 1 control-plane + 1 worker, pinned node image
digest. The two loop devices live inside the **worker** container only
(`/mnt/blkio-e2e/disk{0,1}`, whole disks, ext4, `hack/setup-loopdev.sh`
run via `docker exec`); leave any other kind cluster on the box alone.

`kind-load-busybox` runs `ctr --namespace=k8s.io images pull
docker.io/library/busybox:1.37` inside each node directly instead of
`kind load docker-image`: on this host (Docker Desktop for Mac,
containerd image store) `kind load` fails with `ctr: content digest …
not found` because the exported archive's multi-platform manifest
references blobs the local store never pulled. Pulling straight into each
node's containerd sidesteps that and is what CI uses too — still happens
once during setup, never during a test.

`deploy-kind` restarts the manager on purpose: the tag (`:dev`) never
changes, so without the restart a rebuilt image is never picked up.

For ad-hoc kubectl, always pin: `kubectl --context kind-blkio-limiter ...`.

## Tests

- **Unit + envtest**: `make test` — `go test` (testify, fake client where
  envtest isn't needed) across everything except `test/e2e`, with
  `KUBEBUILDER_ASSETS` set via `setup-envtest`, `CGO_ENABLED=0` (client-go's
  cgo net resolver can't link `-lresolv` on the nix toolchain on darwin — the
  binary needs no cgo, so this is always safe). No ginkgo anywhere in this
  repo (D21) — plain `go test` + `stretchr/testify`.
- **E2E**: build tag `e2e`, real kind cluster (`test/e2e/{harness,agent,operator,hardening}`,
  `hack/kind-config.yaml`, `hack/setup-loopdev.sh`, `hack/e2e-storage.yaml`).
  ```sh
  make e2e-setup   # once: cluster + loop devices + storage class + busybox + deployed manager
  make e2e         # re-runnable, E2E_TIMEOUT (default 30m); go test -p 1 ./test/e2e/...
  ```
  Three packages, all driven from `test/e2e/harness`'s shared clients/builders:
  - `test/e2e/agent` (C3) plays the controller by hand: every test builds
    its own `PodIOLimit` (including the D9 finalizer, removed by the test
    itself). `TestMain` scales `controller-manager` to 0 for the package's
    lifetime (its `PodReconciler` otherwise correctly treats any
    hand-crafted `PodIOLimit` with no matching `IOLimiter` as an orphan and
    deletes it) and **always** restores it to 1 on exit, success or
    failure. Since C7/D27, every write to the main resource
    (create/delete/patch) goes through `harness.ControllerClient`
    (`K8sClient`'s REST config, but impersonating the real controller
    ServiceAccount): the write-restricting VAP means "plays the
    controller" now has to mean authenticating as it too, not just
    replicating its writes as the ambient kind-admin identity. Reads stay
    on the plain `K8sClient` (the VAP only restricts writes).
  - `test/e2e/operator` (C5) drives everything through a real `IOLimiter`,
    controller running throughout. `TestMain` self-heals the controller to
    1 replica and the agent DaemonSet's `nodeSelector` to unset on entry
    (in case a killed prior run, in either package, left either mutated),
    and restores both again on exit.
  - `test/e2e/hardening` (C7) exercises the VAPs (D27) and the narrowed
    cgroup mount (D28) against the real, unmodified deployment: no
    scaling, no patching. Denial tests use `kubectl --as`/`--as-user-extra`
    (impersonation), not the Go client, since that's the actual mechanism
    being proven.

  `make e2e` passes `-p 1`: `go test ./test/e2e/...` otherwise
  builds/runs each package's test binary **concurrently** (bounded by
  `GOMAXPROCS`, independent of `-count=1`), which races `agent`'s and
  `operator`'s `TestMain`s against each other (observed directly:
  `operator`'s self-heal scaling the controller back to 1 while `agent`'s
  tests still assumed it was 0). `-p 1` forces the two packages to run
  strictly one after the other.
  Restarting a container to prove D5 (pod-level cgroup survives it): use
  `crictl stop <containerID>` on the node (read the ID from
  `status.containerStatuses[0].containerID`), not `kubectl exec … kill -9
  1` — verified against busybox `sleep infinity`, SIGKILL to the
  container's own pid 1 from inside its pid namespace does not terminate
  it, `crictl stop` does and lets kubelet's `restartPolicy: Always`
  recreate the container.
  `kubectl logs ds/<name>` silently picks one of the two agent pods
  (control-plane + worker): use `kubectl logs -l control-plane=agent
  --prefix` (both `harness.DumpDiagnostics` and the CI workflow do) to see
  the worker's own log lines; the controller-manager's own single pod is
  `kubectl logs -l control-plane=controller-manager`.
  Waiting for a StatefulSet pod to be recreated with a new UID: don't wait
  for an intermediate NotFound first (`harness.WaitPodGone` then
  `WaitPodRunning`) — the delete-then-recreate can be faster than the
  poll interval, so the gap is never actually observed. Use
  `harness.WaitPodRecreated(t, ctx, ns, name, oldUID, timeout)`, which
  polls for "same name, a *different* UID, Ready" instead.
- **Lint**: `make lint` (golangci-lint, pinned version + the `logcheck`
  module plugin via `.custom-gcl.yml`). `make lint-fix` to auto-fix. Green
  from C0 onward, including `GOOS=linux`.
- `make verify` = lint + test + build; that's the fast local/CI gate.

## Helm chart

`dist/chart` is **generated**, not hand-edited (except
`hack/helm-postprocess.sh` itself). It's checked into git, unlike
`dist/install.yaml` (kustomize's build-installer output, still gitignored):
CI lints and packages the committed chart directly, no kubebuilder CLI
needed in CI.

```sh
make helm-chart   # regenerate dist/chart via kubebuilder helm/v2-alpha, then hack/helm-postprocess.sh
make helm-lint    # helm lint dist/chart
```

`make helm-chart` runs `kubebuilder edit --plugins=helm/v2-alpha --force`
(which itself runs `make build-installer`, i.e. `kustomize build
config/default`, and always renders the chart's default image as
`PUBLISHED_IMG` — the GHCR image — never the local `:dev` tag), then
`hack/helm-postprocess.sh`. The plugin only fully templatizes the manager
Deployment (SPEC.md §8's documented gap, confirmed in C6): the agent
DaemonSet template it emits
(`dist/chart/templates/extras/agent.yaml`) has the image, args, resources,
tolerations, nodeSelector, securityContext and priorityClassName all
hardcoded, and its `serviceAccountName` references a ServiceAccount the
chart never creates (only the manager's SA is templated). The postprocess
script rewrites `agent.yaml` from scratch every run (so re-running
`make helm-chart` is idempotent — verified: diffing two consecutive runs'
`dist/chart` produces no changes) to route the agent onto
`.Values.manager.image` (so `--set manager.image.tag=X` lands on **both**
workloads) and a new `agent:` values block (`args`, `resyncPeriod`,
`allowRootDevice`, `kubepodsCgroup`, `resources`, `tolerations`,
`nodeSelector`, `securityContext`/`podSecurityContext`,
`priorityClassName`), and adds the missing
`dist/chart/templates/rbac/agent-serviceaccount.yaml`. It also deletes the
plugin's own regenerated (unpinned-cluster) `test-chart.yml` workflow every
run, matching the reference `pvc-downsize-operator`: `.github/workflows/ci.yml`
already covers `helm-lint` + a real e2e smoke test against the pinned kind
cluster.

Installing the chart on kind in place of the kustomize deploy (e.g. to spot-
check a chart change before committing):

```sh
make undeploy ignore-not-found=true
IMG=k8s-blkio-limiter:dev make docker-build
kind load docker-image k8s-blkio-limiter:dev --name blkio-limiter
kubectl --context kind-blkio-limiter create namespace k8s-blkio-limiter-system --dry-run=client -o yaml \
  | kubectl --context kind-blkio-limiter apply -f -
kubectl --context kind-blkio-limiter label namespace k8s-blkio-limiter-system \
  pod-security.kubernetes.io/enforce=privileged \
  pod-security.kubernetes.io/audit=privileged \
  pod-security.kubernetes.io/warn=privileged --overwrite
IMG=k8s-blkio-limiter:dev HELM_EXTRA_ARGS="-f hack/kind-values.yaml" make helm-deploy
# ... test, then restore the standard state:
helm --kube-context kind-blkio-limiter uninstall k8s-blkio-limiter -n k8s-blkio-limiter-system
kubectl --context kind-blkio-limiter delete namespace k8s-blkio-limiter-system --ignore-not-found
kubectl --context kind-blkio-limiter delete crd iolimiters.storage.maurice.fr podiolimits.storage.maurice.fr --ignore-not-found
IMG=k8s-blkio-limiter:dev make deploy-kind
```

The Helm chart, unlike `config/default`'s kustomize `namespace_psa_patch.yaml`,
does **not** label the release namespace with the PSA `privileged` labels
the agent's hostPath mounts need (a plain `helm install --create-namespace`
namespace carries no labels) — label it yourself first, as above. kind
doesn't enforce PSA by default, so a chart install there works even without
the labels; a PSA-enforcing cluster needs them.

## API-change checklist

Editing `api/v1alpha1/{iolimiter,podiolimit}_types.go` (fields, CEL rules,
printer columns) always means, in order:

1. Edit the types.
2. `make generate manifests` — regenerates `zz_generated.deepcopy.go`, the
   CRD and RBAC manifests. Never hand-edit those generated files. Run it
   **twice** locally before committing: the second run must produce no diff
   (C0's idempotency acceptance check).
3. If the change touches a CEL rule: prove it in
   `internal/controller/envtest_test.go` (accept/reject table against a real
   apiserver — the fake client never runs CEL). Watch for the apiserver's
   CEL **cost budget**, not just compile errors: a `quantity()`/`isQuantity()`
   call on a field nested under a list with `MaxItems` can exceed the
   budget even with a single call and no comparisons (see the C0 deviation
   note on `IOLimits.readBytesPerSecond`/`writeBytesPerSecond` in SPEC.md —
   there's no controller-gen marker to bound a `resource.Quantity` field's
   `maxLength`, since it rejects `MaxLength` on a non-string Go type).
4. Update `config/samples` if the change affects the example CRs.
5. Update the README's API reference table (from C6).
6. Update this file if the dev workflow itself changed.
7. Update `SPEC.md` (chunk checkboxes, and any deviation forced by reality).

## Conventions

- No ginkgo. `stretchr/testify` (`require` for setup, `assert` for
  non-fatal checks) everywhere, including envtest suites (D21).
- Logging is `logr` via controller-runtime zap in both the manager and the
  agent (D21/D26) — see "Logging & debugging" below.
- `CGO_ENABLED=0` on every `go` invocation, including tool installs (the
  nix cc toolchain can't link `-lresolv` on darwin; neither the manager,
  the agent, nor their tests need cgo).
- Two RBAC roles from markers (D15): `make manifests` runs two separate
  `controller-gen` passes, `rbac:roleName=manager-role` over
  `./internal/controller/...;./cmd/...` (→ `config/rbac`) and
  `rbac:roleName=agent-role` over `./internal/agent/...`
  (→ `config/agent/rbac`), so the agent's least-privilege markers never
  merge into the controller's role or vice versa. CRD/webhook generation
  stays a single pass over `./...`.
- The image transform (`kustomize edit set image controller=${IMG}`) runs
  against `config/default`, not `config/manager`: `config/manager` only
  covers the Deployment, and `config/default` is what also pulls in
  `config/agent`'s DaemonSet. Setting it only in `config/manager` silently
  leaves the agent on the stale image (SPEC.md's C2 deviation notes).
- Docs (`README.md`, this file, `SPEC.md`) are updated in the same change
  as the API/workflow change that motivates them — not as a follow-up.

## Logging & debugging

The manager and the agent (from C2) both run a controller-runtime manager
and log through `logf.FromContext(ctx)` / `ctrl.Log` (logr, zap, `--zap-*`
flags below control it). D26 is the source of truth; the key vocabulary is
literal strings at each call site (not shared Go constants — the
`logcheck` linter requires key arguments to be inlined literals):

| Key | Meaning |
|---|---|
| `pod` | `<ns>/<name>` of the target pod (on every agent and PodReconciler line) |
| `podUID` | pod UID |
| `iolimiter` | `<ns>/<name>` of an IOLimiter (on every IOLimiterReconciler line; `sources` lists them on merge lines) |
| `podiolimit` | `<ns>/<name>` of the PodIOLimit |
| `node` | node name |
| `volume` | pod volume name |
| `kubeletDir` | `kubeletDirName` (PV name or volume name) |
| `mountPoint` | host mount point matched in mountinfo |
| `mountDevice` | `MAJ:MIN` from mountinfo |
| `device` | whole-disk `MAJ:MIN` actually throttled |
| `partitionOf` | set when `mountDevice` was a partition (the mapping) |
| `cgroup` | pod cgroup path relative to the cgroup root |
| `path` | full `io.max` path written |
| `before` / `after` | the device's `io.max` line before the write and on read-back (`<none>` = no line = max) |
| `rule` | the four-key rule written |
| `op` | `apply` / `reset` / `release` |
| `state` / `from` / `to` | volume/device state, or a transition's endpoints |
| `reason` | why (the §4.2 reason vocabulary, or a skip reason) |
| `generation` / `observedGeneration` | spec generation handled |
| `finalizer` | finalizer name on add/remove |
| `elapsed` | time since first seen `Pending` |

Levels (SPEC.md §6.3 is the source of truth; summarised here):
- **Info** (default): every state change and every mutating API/kernel
  write the controller or agent makes. Never unchanged state on every poll
  or resync.
- **V(1)** (`--zap-log-level=debug`): waits, requeues, no-ops, and status
  write conflicts (a conflict just means the cache was stale, not an
  error).
- **Errors**: returned (`fmt.Errorf("...: %w", err)`), not both logged and
  returned — controller-runtime already logs a `Reconcile` error once when
  it retries.
- Transitions and events are emitted **after** the status write succeeds,
  so a conflicted write never logs/emits the same transition twice.

Raising verbosity on a running (e.g. kind) deployment:

```sh
kubectl --context kind-blkio-limiter -n k8s-blkio-limiter-system patch deployment \
  k8s-blkio-limiter-controller-manager --type=json \
  -p '[{"op":"add","path":"/spec/template/spec/containers/0/args/-","value":"--zap-log-level=debug"}]'
```

The agent DaemonSet takes the same flag the same way (`kubectl ... patch
daemonset k8s-blkio-limiter-agent --type=json -p '[...]'`, same JSON patch
shape, appended to its existing args).

`--zap-log-level` (`debug`/`info`/`error` or an integer), `--zap-encoder`
(`json`/`console`) and `--zap-devel` are the standard controller-runtime zap
flags (`cmd/main.go`, `zap.Options.BindFlags`). Defaults: console encoder
(development mode, human-readable) at **info** level — development mode
alone would default to debug, `cmd/main.go` pins `Level: zapcore.InfoLevel`.
Use `--zap-encoder=json` for log aggregation.

Following one object end to end (the controller and the agent each write
their own narrative lines, from C4/C2 respectively):

```sh
kubectl -n k8s-blkio-limiter-system logs deploy/k8s-blkio-limiter-controller-manager | grep '<ns>/<name>'
kubectl -n k8s-blkio-limiter-system logs ds/k8s-blkio-limiter-agent | grep '<ns>/<pod>'
```

## Gotchas learned the hard way

- **CEL cost budget beats CEL compilation.** A `resource.Quantity` (int-or-
  string) field validated via `quantity()`/`isQuantity()` inside a list with
  `MaxItems` can compile fine but still be rejected at CRD-install time
  with "estimated rule cost exceeds budget" — even a single, bound-free
  call. There's no marker to bound the field's `maxLength` (controller-gen
  refuses `MaxLength` on a non-string Go type). See SPEC.md's C0 deviation
  note on `IOLimits`; the numeric range/whole-number check moved to a
  controller-side check instead of CEL.
- **`make manifests generate` must be run twice** before trusting the
  output is committed cleanly — the C0 acceptance check is that the second
  run produces no diff.

## Kubebuilder scaffold rules

- Never hand-edit generated files: `config/crd/bases/*.yaml`,
  `config/rbac/role.yaml`, `**/zz_generated.*.go`, `PROJECT`. Regenerate with
  `make manifests generate`.
- Never remove `// +kubebuilder:scaffold:*` markers — the CLI injects code
  at these markers.
- Use `kubebuilder create api` to scaffold new APIs, not hand-written files.
